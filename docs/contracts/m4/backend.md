# M4 — contrato de backend para datasets, treinamento e versões

Estado: contrato de implementação; não autoriza execução na P7 nem ativação de rotas antes da migração, das credenciais e da política de GPU. Horários são instantes RFC 3339 em UTC (`Z`). Toda rota abaixo de `/api` exige sessão BFF, função `user` e, para métodos inseguros, o cabeçalho CSRF e `Origin` exato do M1. `owner_sub` vem exclusivamente das claims; recursos de outro usuário respondem 404. Nenhum token vai ao navegador.

## Dataset privado

`POST /api/training/datasets` recebe `multipart/form-data` com `name` (1–120 caracteres) como primeira parte e `file` JSONL como segunda parte. Limite: **32 MiB**, 1–5000 linhas não vazias, até **32.768 bytes UTF-8 por linha**. Cada objeto tem exatamente `instruction` (string não vazia), `input` (string opcional; ausente equivale a `""`) e `output` (string não vazia); cada campo tem até **8192 bytes UTF-8**. Exigir UTF-8 válido, objeto JSON por linha, sem campos extras, sem BOM, sem duplicação de chaves e sem linhas em branco. A validação ocorre em streaming antes de tornar o objeto visível; falhas removem upload parcial. Hash SHA-256 é do JSONL original validado. O bucket `ia-trainner-datasets` é privado e sua chave nunca aparece na API, nos eventos nem em logs.

Resposta `201` com `Location: /api/training/datasets/{id}` e `DatasetSummary`:

```json
{"id":"uuid","name":"Exemplo","status":"ready","rowCount":12,"sizeBytes":1234,"sha256":"64 hex","createdAt":"2026-09-26T12:00:00Z"}
```

`GET /api/training/datasets` retorna `{ "items": [DatasetSummary], "nextCursor": string|null }` em ordem decrescente de `(createdAt,id)`, com `limit` 1–100 (padrão 25) e `cursor` opaco base64url; `GET /api/training/datasets/{id}` retorna o resumo. A primeira entrega não inclui exclusão física. Duplicata de conteúdo do mesmo proprietário retorna `409 dataset.duplicate` com o ID existente, sem copiar objeto. Erros: `400 request.invalid`, `413 dataset.too_large`, `422 dataset.invalid` com `line`/`field` seguros, `503 service.unavailable` quando PostgreSQL/S3/configuração faltam.

## Catálogo, agendamento e estado

`GET /api/training/catalog` retorna a lista fixa de perfis permitidos quando a configuração M4 da API está habilitada:

```json
{"models":[{"baseModel":"Qwen/Qwen2.5-0.5B-Instruct","trainingProfile":"lora-v1","maxSteps":{"min":1,"max":100,"default":10},"maxSeqLength":1024}],"datasetLimits":{"maxBytes":33554432,"maxRows":5000,"maxLineBytes":32768,"maxFieldBytes":8192},"windowBudget":{"preparationSeconds":600,"executionSeconds":3600,"evaluationSeconds":600,"recoverySeconds":600,"minimumWindowSeconds":4800,"minimumEvaluationWindowSeconds":1800}}
```

Os números de `windowBudget` acima são apenas exemplo de formato: a resposta real usa os orçamentos configurados pelo operador. A imagem Python vem do ConfigMap privado lido pelo Worker e é validada como digest antes de criar um Job; o catálogo não consulta esse ConfigMap ao vivo nem expõe digest, chave, caminho S3 ou configuração Kubernetes. A API retorna 503 nas rotas M4 quando sua flag ou configuração obrigatória falta. A readiness do Worker, separadamente, verifica PostgreSQL, tópicos Kafka e o digest no ConfigMap antes da ativação operacional.

`POST /api/training/jobs` recebe:

```json
{"datasetId":"uuid","baseModel":"Qwen/Qwen2.5-0.5B-Instruct","trainingProfile":"lora-v1","maxSteps":10,"maxSeqLength":1024,"window":{"startsAt":"2026-09-27T02:00:00Z","endsAt":"2026-09-27T04:00:00Z"},"clientRequestId":"uuid"}
```

`maxSteps` omitido usa 10; os demais campos são obrigatórios. Só dataset `ready` do proprietário. Persistir janela em UTC e rejeitar duração/antecedência que não comportem preparação, execução máxima e recuperação. O agendador consulta PostgreSQL quando a janela se torna elegível; não usa mensagens Kafka com atraso longo. Resposta `202`, `Location: /api/training/jobs/{id}` e `TrainingJobDetail`. Mesmo `clientRequestId` + mesma configuração devolve o mesmo trabalho; mesma chave + configuração diferente retorna `409 training.idempotency_conflict`.

`GET /api/training/jobs` retorna `{ "items": [TrainingJobSummary], "nextCursor": string|null }` com o mesmo `limit`/`cursor` de datasets, apenas trabalhos de treino. `TrainingJobSummary` contém `id,datasetId,baseModel,status,cancelRequested,attempt,window,createdAt,updatedAt,modelVersionId`; `GET /api/training/jobs/{id}` retorna:

```json
{"id":"uuid","datasetId":"uuid","baseModel":"Qwen/Qwen2.5-0.5B-Instruct","trainingProfile":"lora-v1","maxSteps":10,"maxSeqLength":1024,"window":{"startsAt":"...Z","endsAt":"...Z"},"status":"scheduled","cancelRequested":false,"attempt":0,"version":1,"createdAt":"...Z","updatedAt":"...Z","startedAt":null,"finishedAt":null,"failureCode":null,"progress":null,"modelVersionId":null}
```

`progress` é `{ "completedSteps": int, "totalSteps": int, "observedAt": "...Z" }` apenas quando confirmado pelo executor; não é previsão. `POST /api/training/jobs/{id}/cancel` não recebe corpo e devolve `202` com o detalhe atualizado. Cancelamento de `scheduled` conclui quando o Worker o reconcilia; trabalho que reservou GPU só chega a `canceled` depois de remover o Job Kubernetes e restaurar a inferência. Cancelamento repetido é idempotente. `POST /api/training/jobs/{id}/retry` aceita `{ "window": {"startsAt":"...Z","endsAt":"...Z"}, "clientRequestId":"uuid" }` apenas após `failed` ou `canceled`, cria **novo trabalho** com `previousJobId` apontando para o trabalho terminal e nova janela, devolvendo `202`, `Location` e detalhe do novo ID. O trabalho e `clientRequestId` originais permanecem imutáveis; replay da requisição de retry devolve o mesmo novo ID.

Todos os treinos **e avaliações** são `training_jobs` com `kind=training|evaluation`; passam pela mesma janela, fila, reserva GPU, cancelamento e reconciliação. Estados comuns: `scheduled → reserving → draining → running → restoring → succeeded`; a avaliação passa de `running` para `evaluating` antes de `restoring`. Falha/cancelamento em qualquer fase após reserva passa por `restoring` antes de `failed`/`canceled`. `cancelRequested` é sinal durável separado do estado. Estado oficial, tentativa, versão e timestamps ficam no PostgreSQL. Uma única reserva da GPU P7 existe por vez; lease expirado **não** libera outra execução antes de reconciliar Job Kubernetes e Ollama. Nenhum início após `endsAt - (executionBudget + recoveryBudget)`; ao fim da janela, cancelar o Job e restaurar inferência. `409 training.window_invalid`, `409 training.not_retryable` e `503 service.unavailable` usam Problem Details existente.

## Versão do modelo e avaliação real

Um treino bem-sucedido só cria `ModelVersion` após verificar no bucket privado `ia-trainner-artifacts` a identidade do resultado (`operation`, `executionId`, status), a chave, o hash SHA-256, o tamanho e o formato `peft-lora` do artefato, e métricas finitas. Modelo base, dataset e configuração vêm do trabalho persistido no PostgreSQL e do manifesto construído pelo Worker; o resultado Python não os repete. `GET /api/training/model-versions` retorna `{ "items": [ModelVersionSummary], "nextCursor": string|null }` com o mesmo `limit`/`cursor`; `GET /api/training/model-versions/{id}` inclui linhagem e métricas. DTO:

```json
{"id":"uuid","jobId":"uuid","datasetId":"uuid","baseModel":"Qwen/Qwen2.5-0.5B-Instruct","adapterFormat":"peft-lora","status":"ready","artifactSha256":"64 hex","artifactSizeBytes":1234,"metrics":{"trainLoss":1.23},"createdAt":"...Z","selectedAt":null}
```

`POST /api/training/model-versions/{id}/select` marca explicitamente a versão do proprietário como `selected` e retorna o detalhe (`200`); a selecionada anterior volta a `ready` na mesma transação. `selected` registra uma preferência durável do proprietário; avaliações nesta entrega ainda indicam explicitamente o ID da versão. Não significa modelo Ollama já instalado ou chat disponível. `GET /api/training/model-versions/{id}/artifact` faz download autenticado em streaming, com nome neutro, sem URL S3 pré-assinada no navegador. Sem seleção implícita ao fim do treino.

`POST /api/training/model-versions/{id}/evaluations` recebe `{ "instruction":"...", "input":"", "window":{"startsAt":"...Z","endsAt":"...Z"}, "clientRequestId":"uuid" }`; campos seguem limite de 8192 bytes UTF-8, e a pergunta fica em objeto S3 privado. **A janela UTC é obrigatória também para avaliação**; nenhuma avaliação pausa o Ollama fora da janela. Resposta `202`, `Location: /api/training/evaluations/{id}`, com `{id,jobId,modelVersionId,status,window,createdAt}`. O `jobId` é um `training_jobs.id` de `kind=evaluation`, igual ao `id` da avaliação para simplificar correlação. O Job Python avalia **base e adapter reais**, com mesma entrada, e grava respostas e métricas em S3 privado; não cria nome fictício no Ollama. `GET /api/training/evaluations/{id}` retorna `id,jobId,modelVersionId,status,window,cancelRequested,createdAt,updatedAt,failureCode` e, após sucesso, `{base:{text,inputTokens,outputTokens,durationMs},adapter:{text,inputTokens,outputTokens,durationMs}}` lidos do resultado privado após autorização; os três números são inteiros não negativos exigidos no resultado bem-sucedido, nunca estimados como reais. `POST /api/training/evaluations/{id}/cancel` segue a mesma semântica de cancelamento durável de treino e retorna `202`. Falha retorna `failureCode` seguro. Conteúdo de dataset, prompt, resposta, credenciais e URLs assinadas nunca entram em Kafka, manifesto Kubernetes, OTel ou logs. O manifesto privado do Job contém somente referências opacas a objetos S3, necessárias ao Python; essas chaves não aparecem na API, Kafka, OTel ou logs.

## PostgreSQL V0004 — colunas necessárias

Reusar `ia_trainner.outbox_messages`. Mensagens de treinamento usam tópico próprio `ia-trainner.training.v1` e DLQ própria, schema v1, contendo apenas metadados de evento (`messageId`, `type`, `aggregateId`, `aggregateVersion`, `ownerSub`, `organizationId:null`, `occurredAt`, `data.jobId`) e trace context; nenhum conteúdo ou chave S3. Kafka acorda o Worker; o scan PostgreSQL permanece fonte durável e cobre sinais perdidos/duplicados. Avisos inválidos vão à DLQ em envelope seguro, sem republicar o payload original. Não usar o tópico de documentos.

## Portas e execução

Application define `ITrainingUnitOfWork` com repositórios de dataset/job/model/evaluation e outbox, além de `ITrainingWorkerUnitOfWork`/`ITrainingWorkerStore` para tentativa, reserva e reconciliação. Reusa `IObjectStorage` com `BucketKind.Datasets/Artifacts` e `IClock` existentes. Worker usa `TrainingWorkCoordinator`, `IKubernetesTrainingJobs` e `IGpuCoordinator`; `TrainingResultVerifier` valida resultado/artefato no armazenamento privado. Nenhuma porta de API expõe operações sem filtro de proprietário. Worker constrói manifesto Kubernetes apenas com imagem por digest, comandos e recursos de catálogo fixos; entradas do usuário são IDs e referências privadas, jamais shell/env livre. Job Python usa Secret runtime S3 com leitura de datasets e leitura/escrita de artifacts. Reconciler consulta SQL + Kubernetes + Ollama após reinício, drena inferência, confirma a saída do pod Ollama, cria Job idempotente, observa execução, interrompe ao cancelar/expirar e restaura inferência antes do estado terminal. Kafka acorda o Worker; PostgreSQL decide o trabalho elegível e a verdade do estado.

`/api/platform` mantém `training` (M4) e acrescenta `models` (M4). Ambos começam `unavailable` e ficam `available` quando a flag M4 da API e sua configuração obrigatória estão presentes. Esse indicador não consulta a disponibilidade da GPU, o ConfigMap de imagem nem a saúde ao vivo do Worker; a readiness separada do Worker verifica essas dependências antes da ativação operacional. A interface consulta status real de cada trabalho. Não alterar o status de M1/M2/chat por falha de M4.

Erros seguem `application/problem+json` com `code` estável e `traceId`, sem conteúdo privado. Códigos M4: `dataset.invalid` 422, `dataset.too_large` 413, `dataset.duplicate` 409, `dataset.not_found` 404, `training.window_invalid` 409, `training.idempotency_conflict` 409, `training.not_retryable` 409, `training.job_not_found` 404, `model_version.not_found` 404, `model_version.not_ready` 409, `evaluation.not_found` 404, `evaluation.invalid` 422, `service.unavailable` 503. Validação de campos usa `validation.failed` 422, tipo/body usa `request.invalid` 400 ou `request.unsupported_media_type` 415. Configuração incompleta retorna 503 só nas rotas M4; M1/M2/chat permanecem operantes. Testes CPU/Docker verificam validação, isolamento, idempotência e reconciliação; smoke GPU real e consumo do adapter exigem janela autorizada e são critérios pendentes até execução comprovada.

## Manifest e resultado Python v1

Worker entrega **um único** `FINETUNING_JOB_MANIFEST` JSON por Job, não secreto, construído apenas de dados persistidos e configuração de catálogo. Chaves seguem prefixo determinístico: dataset `datasets/{ownerHash16}/{datasetId}/original.jsonl` no bucket datasets; execução `executions/{executionId}/` no bucket artifacts; avaliação `executions/{executionId}/request.json`, resultado `executions/{executionId}/result.json`, adapter de treino `executions/{executionId}/adapter.tar.gz`. `ownerHash16` é prefixo SHA-256 do `owner_sub` em hex minúsculo, como no M2. `executionId` é UUID estável da tentativa ou avaliação; retry cria novo ID. Referências S3 no manifest são nomes de objetos, nunca credenciais ou URLs.

Treino:

```json
{"schemaVersion":1,"operation":"training","executionId":"uuid","trainingId":"uuid","datasetId":"uuid","dataset":{"key":"datasets/.../original.jsonl","sha256":"64 hex","bytes":1234,"rows":12},"baseModel":"Qwen/Qwen2.5-0.5B-Instruct","trainingProfile":"lora-v1","maxSeqLength":1024,"artifactKey":"executions/.../adapter.tar.gz","resultKey":"executions/.../result.json","budget":{"maxSteps":10,"maxDurationSeconds":3600,"maxRows":5000,"maxDatasetBytes":33554432,"maxFieldBytes":8192,"maxNewTokens":256},"windowEndsAt":"...Z","traceparent":"00-..."}
```

Avaliação:

```json
{"schemaVersion":1,"operation":"evaluation","executionId":"uuid","trainingId":"uuid","datasetId":"uuid","modelVersionId":"uuid","baseModel":"Qwen/Qwen2.5-0.5B-Instruct","adapter":{"key":"executions/.../adapter.tar.gz","sha256":"64 hex","bytes":1234},"request":{"key":"executions/.../request.json","sha256":"64 hex","bytes":123},"resultKey":"executions/.../result.json","budget":{"maxDurationSeconds":600,"maxFieldBytes":8192,"maxNewTokens":256},"windowEndsAt":"...Z","traceparent":"00-..."}
```

O arquivo de pedido da avaliação é JSON `{ "instruction": string, "input": string }` no S3 privado; o manifest **não** contém o texto. O Python verifica schema, prefixo de chaves, hashes/tamanhos, orçamento e modelo permitido antes de carregar dataset/adapter. Credenciais S3 vêm do Secret runtime do Job, com leitura de datasets e leitura/escrita de artifacts; jamais do manifest.

O Python faz upload de `result.json` **por último**, após adapter/saídas completas. Formato de sucesso treino: `{schemaVersion:1,operation:"training",executionId:"uuid",status:"succeeded",adapter:{key,sha256,bytes,format:"peft-lora"},metrics:{trainLoss:number,completedSteps:int,durationMs:int}}`. Sucesso avaliação: `{schemaVersion:1,operation:"evaluation",executionId:"uuid",status:"succeeded",base:{text,inputTokens,outputTokens,durationMs},adapter:{text,inputTokens,outputTokens,durationMs}}`. Falha: `{schemaVersion:1,operation,executionId,status:"failed",failureCode:"código seguro"}`; nenhum traceback, token, prompt ou URI com segredo. Worker valida resultado contra IDs/prefixos/hash e números finitos antes de promover estados; Job Kubernetes `Complete` sem `result.json` válido é falha, não sucesso. `progress.json` não é consumido pelo Worker nesta entrega; `progress` na API permanece nulo sem atualização confirmada no PostgreSQL.
